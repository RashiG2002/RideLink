# RideLink Fare & Payment Service

Member 4 service for fare estimation, final fare calculation, simulated payments, payment status, and receipts.

## Responsibilities and data ownership

This service owns the `payments` and `receipts` MongoDB collections. It does not read or write another service's database. `rideId` and `passengerId` are stable identifiers supplied by the Ride Management and Account services through the agreed API contract.

Authentication and role enforcement are provided by the shared Account Service or API gateway. The gateway must validate the bearer token and forward the authenticated identity and role before exposing payment operations.

## Fare rule

All amounts are simulated currency units:

- Base fare: 250
- Distance charge: 10 per kilometre
- Service charge: 50
- Peak-hour multiplier for final fare: 1.5

Therefore:

`estimatedFare = 250 + (distanceInKm * 10) + 50`

`finalFare = estimatedFare * 1.5` during peak hours; otherwise `estimatedFare`.

Distances must be finite and strictly positive. Payment amounts are calculated by this service from the supplied ride distances; clients do not provide an amount.

## Run

Prerequisites: Java 17, Maven, and MongoDB running locally.

```text
mvn spring-boot:run
```

The service runs on port `8088` and uses the isolated database `ridelink_payment_db`. For local development, the default connection is `mongodb://localhost:27017/ridelink_payment_db`. For another MongoDB instance, set the `MONGODB_URI` environment variable before starting the service; do not commit credentials.

Windows PowerShell example:

```powershell
$env:MONGODB_URI = "mongodb://username:password@localhost:27017/ridelink_payment_db?authSource=admin"
mvn spring-boot:run
```

Windows Command Prompt example:

```cmd
set MONGODB_URI=mongodb://username:password@localhost:27017/ridelink_payment_db?authSource=admin
mvn spring-boot:run
```

## API

Swagger UI: `http://localhost:8088/swagger-ui.html`

- `POST /api/v1/fares/estimate` - estimate a fare from `distanceInKm`
- `POST /api/v1/fares/calculate-final?actualDistance={km}&isPeakHour={true|false}` - calculate final fare
- `POST /api/v1/fares/pay` - record a simulated payment with `CARD`, `CASH`, or `WALLET`
- `POST /api/v1/fares/pay/by-distance` - calculate the amount from the entered distance, optionally adjust it using actual distance, then record payment
- `POST /api/v1/fares/pay/pending` - create a pending payment for asynchronous-processing demonstration
- `POST /api/v1/fares/payment/{rideId}/process` - update a pending payment to `SUCCESS` or `FAILED`
- `GET /api/v1/fares/payment/{rideId}` - retrieve payment status
- `GET /api/v1/fares/receipt/{rideId}` - retrieve a successful payment receipt

GET aliases for the estimate and payment operations are retained for compatibility with the shared Postman collection. Payment GET requests now take `user`, `rideId`, `passengerId`, `distanceInKm`, optional `actualDistanceInKm`, `isPeakHour`, and `paymentMethod` query parameters; they do not accept `amount`.

To demonstrate the failed-payment negative scenario deterministically, submit `paymentMethod: "DECLINED"` or `"FAIL"`. A receipt is generated only for successful payments. Payment status is generated by the service and is never supplied by the client.

For dynamic payment calculation, call `POST /api/v1/fares/pay/by-distance` with `user`, `rideId`, `passengerId`, `distanceInKm`, `isPeakHour`, and `paymentMethod`. The service calculates `250 + (distanceInKm * 10) + 50`, applies the peak multiplier when requested, and stores the calculated result as the payment amount. The client does not submit the amount.

To adjust the amount using an actual distance, also send `actualDistanceInKm`. The entered distance remains `distanceInKm`; the final fare is corrected by `(actualDistanceInKm - distanceInKm) * 10`, equivalent to calculating the fare directly from measured distance. A greater actual distance increases the estimate and a smaller actual distance decreases it. Peak pricing is applied to the corrected fare. If `actualDistanceInKm` is omitted, the endpoint uses `distanceInKm`. The response includes the computed `amount` and service-generated `status`. On successful payment, the receipt's `totalFare` is copied from the payment's `amount`.

To demonstrate the pending state, call `POST /api/v1/fares/pay/pending` with the same user, ride, distance, and payment-method fields. The service calculates and stores the amount with `PENDING` status and does not generate a receipt.

To update that MongoDB payment, call `POST /api/v1/fares/payment/{rideId}/process`. A normal method such as `CARD` becomes `SUCCESS` and generates a receipt; `FAIL` or `DECLINED` becomes `FAILED`. Processing a non-pending payment returns HTTP `409`.

A ride can have only one successful payment. A repeated successful payment request for the same `rideId` returns HTTP `409` and does not create another payment or receipt. Failed payments may be retried according to the Ride Management service workflow.

## Payment state transitions

```text
PENDING -> SUCCESS -> receipt generated
PENDING -> FAILED  -> no receipt
SUCCESS -> no transition; duplicate payment returns HTTP 409
FAILED  -> no transition; a new payment request may be submitted as a retry
```

## Integration contract

Ride Management owns the ride lifecycle and calls this service after completion. It supplies the trusted user identity, stable `rideId` and `passengerId`, and entered/actual distance values. This service calculates the fare and owns payment status, persistence, simulated payment outcomes, and receipt generation; it does not access the Ride Management database.

Expected client handling:

- `200`: fare calculated, payment retrieved, or payment completed
- `201`: pending payment created
- `400`: invalid request or simulated failed payment
- `404`: payment or receipt does not exist
- `409`: payment is not pending or a successful payment already exists

Authentication and role enforcement are provided by the shared Account Service/API gateway. The gateway must validate the bearer token and forward the authenticated identity and role before exposing payment or receipt operations.
